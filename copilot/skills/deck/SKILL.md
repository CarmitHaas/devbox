# Deck

## What this skill does
Takes a topic plus its material (notes, a DASHBOARD.md and sessions folder, a design doc, a chat) and produces a .pptx the user can open in PowerPoint and present. The outline is agreed before any slide is built. The deck is generated by code from `skeleton.mjs` (PptxGenJS) or `skeleton.py` (python-pptx) so it can be rebuilt after a correction. Output is the file plus a short QA report.

## When to use it
- "Make a deck about <topic>"
- "Build the status slides from the brain"
- "Turn these notes into a presentation for <audience>"

Do not use it for a document people will read on their own; use `explainer-page`. Do not use it for an architecture picture; use `architecture-diagram` and then place the exported PNG on a slide.

## How to do it
1. Read: all the material. Note the audience, the time slot (one slide per 1 to 2 minutes), and the decision or feeling the deck must leave behind. If the input is a brain, see "Deck from a brain" below.
2. Decide the outline and show it before building. Rules: one idea per slide; every title is a full sentence that states the idea ("Build time doubled since the agent pool shrank", not "Build time"); at most 6 bullets per slide, each under 12 words; a section slide every 4 to 6 content slides; the last slide is the "so what": the decision, the ask, or the next three steps. Every slide gets speaker notes: what to say, what to skip when short on time.
3. Ask: does the organization have a .potx or .pptx template? If yes, ask for the file and build on it with python-pptx (`skeleton.py`), the one library here that opens an existing template; a .potx must first be saved as .pptx from PowerPoint. If no template, use the neutral palette in `skeleton.mjs` (five tokens: BRAND, BRAND_SOFT, INK, MUTED, ACCENT) and tell the user to replace them with the organization's values. Ask one question at a time. Never guess a brand color or a logo.
4. Check: Node present? `node --version` (22 is fine). Then `npm i pptxgenjs` in a scratch folder and copy `skeleton.mjs` next to it. No Node? `pip install python-pptx` and use `skeleton.py`. Both files live next to this SKILL.md.
5. Write the build script from the skeleton: one function call per slide type (title, section, bullets with notes, two columns, closing). Fill it from the agreed outline. Run it: `node build.mjs` or `python3 build.py`. Fix errors in the script, never by hand-editing the .pptx, so the deck can be regenerated.
6. QA, in PowerPoint (from WSL: `explorer.exe out.pptx`, or copy to the Windows side). Go through the list below and fix in the script. One pass, then stop.
7. Report in the format below. Say what you assumed.

### QA list
- Open the file; it opens without a repair prompt.
- View > Slide Sorter: no orphan slide (a section slide with nothing after it, a slide the outline does not account for, a leftover placeholder).
- No text overflow: no text touching the slide edge, no auto-shrunk text. Shorten the text or split the slide.
- Font sizes: titles 28 or larger, body and bullets 14 or larger, footer 10 or larger. Nothing smaller.
- Contrast: dark text on light fill or light text on dark fill. Nothing on a mid-tone.
- Footer identical on every slide except the title slide: short deck name, slide number, and the classification line if the organization uses one.
- Speaker notes present on every slide (View > Notes Page).
- Every content slide has at least one visual element (a shape, a table, a chart, an icon, a picture). No slide that is only a block of text.

### Deck from a brain
A brain is a folder with `DASHBOARD.md` (current state) and dated notes in `sessions/`. For a status deck:
1. Read `DASHBOARD.md` for the trackers, the this-week table, and the open questions. Read the `sessions/` notes dated since the last status (or the last five) for what actually happened.
2. Outline: title; where we are (the trackers, as a table or progress bars); done since last time (from sessions, dated, three to five items); blockers and open questions (owner per item, as a role); next period; so what (the asks).
3. Pull numbers and dates verbatim from the brain. Do not round or improve them. Write `TODO:` where the brain is silent.
4. Names: role labels unless the user says the deck stays inside the team. Before the deck leaves the team, list every name, hostname, ticket key and internal link it contains and ask which to keep.

## What not to do
- Do not build before the outline is agreed; a rebuilt deck costs more than a reworded outline.
- Do not write a title that is a noun ("Jenkins"); write the sentence the slide proves.
- Do not put more than one idea or more than 6 bullets on a slide; split it.
- Do not use a `#` prefix in PptxGenJS hex colors; it corrupts the file.
- Do not reuse one options object across `addText` or `addShape` calls; PptxGenJS mutates them. Build a fresh object each time (the skeleton does).
- Do not place content in the footer zone (bottom 0.6 inch).
- Do not add decorative lines under titles or clip-art; a chart or a real screenshot earns its place, decoration does not.
- Do not invent a brand palette or draw a logo; ask for the template or ship the neutral tokens and say so.
- Do not hand-edit the .pptx after generation; fix the script.

## Output format
```
Deck: <file name>.pptx  (<N> slides, <M> minutes at 1.5 min per slide)
Built with: PptxGenJS | python-pptx on <template file or "neutral palette">
Outline:
 1. <title sentence>            [title]
 2. <title sentence>            [bullets, notes]
 ...
 N. <so what: the ask>          [closing]
QA: opens <ok>, overflow <none | slide X fixed>, fonts <ok>, contrast <ok>, footer <ok>, notes <N/N>, orphans <none>
Assumed: <palette, audience, time slot, anything guessed>
Replace before sending: <names, hosts, keys found, or "nothing">
```
